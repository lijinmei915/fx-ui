# 错误模式记录

> 每次犯错后立即记录，防止同样的错误再犯。
> 跟 `docs/DECISIONS.md` 的分工：这里记"犯了什么错、加了什么规则"，DECISIONS 记"选了什么方案、为什么"。

---

## 如何记录一条教训

```markdown
### LES-001: 简述犯了什么错

- **日期**：YYYY-MM-DD
- **犯的错**：具体做了什么错误操作
- **根本原因**：为什么会犯这个错（流程缺失 / 理解偏差 / 工具限制）
- **造成的影响**：影响了什么、花了多久修复
- **加了什么规则**：为防止再犯，新增了什么约束或检查
```

## 教训列表

### LES-001: 杜撰了 shadcn 不存在的"文字按钮"概念

- **日期**：2026-06-07
- **犯的错**：在 Button 场景示例里编了一个标题叫"文字按钮"/"Text Button"的场景，暗示这是 shadcn 里一个有意义的 UX 分类，实际 shadcn 根本没有这个说法，真实变体名叫 `ghost`
- **根本原因**：凭"经验/印象"现造了一个看起来合理的概念名词，落笔前没有去查 shadcn 的真实变体命名
- **造成的影响**：被用户当场抓包反问"文字按钮在 shadcn 有么 一切都不要杜撰"，需要承认错误、改名为"Ghost 操作"/"Ghost action"，并在文案里显式注明"shadcn 里官方就叫 ghost"，避免同样的误导留在文档里
- **加了什么规则**：但凡要在文档里给组件变体、API、属性起名字或下定义，必须先去源码或官方文档核实它是否真实存在，绝不能凭印象现造概念后再包装成"看起来对"的说法

### LES-002: 给 Base UI 组件文档套用了 Radix 的概念

- **日期**：2026-06-07
- **犯的错**：准备给 Button 的 Props 表加一个 `asChild` 属性——这是 Radix 生态的常见 prop，但没有先确认 fx-ui 的 Button 底层到底是不是 Radix
- **根本原因**：shadcn 生态里大量组件基于 Radix，凭"通识"想当然地认为这里也是 Radix，没有先打开 `button.tsx` 看一眼 import
- **造成的影响**：在写入文档前自查时发现 `button.tsx` 实际 `import { Button as ButtonPrimitive } from "@base-ui/react/button"`——底层是 Base UI，`asChild` 根本不存在；及时改为记录 Base UI 的真实等价属性 `render`，避免了文档上线后再被纠错
- **加了什么规则**：给任何"看起来眼熟"的组件写文档前，先读一遍源码确认底层库是谁，不要用同生态里别的库的概念去套——这条本质和 LES-001 是同一类问题（先核实，再下笔）

### LES-003: 为满足白字对比度绕开既定 Map 另造按钮色阶

- **日期**：2026-08-28
- **犯的错**：系统已经约定实心交互使用 09/08/10，却又在 Map 中增加 `solid-50/60/70`，并让 Semantic 主按钮和功能色改为消费这套更暗的颜色。
- **根本原因**：把“按钮前景文字要满足对比度”错误地当成“可以修改按钮背景色来源”，没有守住 Map 色阶与 Semantic 映射的单一链路。
- **造成的影响**：网页、Theme contract、Semantic 和组件 Hook 虽彼此一致，却共同偏离了用户确认的交互阶梯；默认橙色按钮明显偏暗偏棕，Foundation 同时存在两套含义重叠的实心颜色。
- **加了什么规则**：交互背景必须由合同中的 Base 90/80/100/50 映射；前景对比度必须用独立 Semantic 解决。审计失败只能推动前景或合同评审，不能静默生成第二套背景色阶。
